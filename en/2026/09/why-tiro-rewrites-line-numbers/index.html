Why Tiro rewrites every line number its model cites

30 September 2026 · writing · history

Tiro is a desktop assistant for Turkish criminal defense lawyers. The case file stays on the laptop, so the chat model is small: Gemma 4 E4B, 4-bit quantized, running through llama.cpp. It cites the file like this: “(Belge 3, satır 34)”, document 3, line 34. The lawyer clicks it and the document opens with those lines highlighted. A wrong line number is worse than none, because it looks checked. This post is about the pass that decides which line numbers the lawyer actually sees.

The failure

Our public demo case is “Doğu Ekspresi Cinayeti”, a fictional file loosely based on Murder on the Orient Express. Here is a citation of the kind the model produced when asked about the victim’s blood alcohol, kept in the repo as a regression test:

Maktulün kanında 1.8 promil alkol tespit edilmiştir (Belge 3, satır 37/1).

The sentence is right. Document 3 is the autopsy report, also right. “37/1” is not a line. It looks like TCK 37/1, the joint perpetration article that the demo indictment charges under. The model took a number-shaped string from somewhere in its context and put it where the line number goes. The value is on line 34.

This was not a rare case. Before this work, 4 of 52 line citations on our demo eval pointed at lines that contained the answer.

Why a small model gets this wrong

A line number has no semantic link to the claim. The model paraphrases “1.8 promil alkol” well because the words carry meaning; “34” carries none. A 4B model at Q4 is weak at this kind of copying, and the context is full of competing numbers: article numbers, dates, times, and the line labels of other passages.

So I stopped treating the model’s line numbers as data. The model decides which sentence it is supporting and which document it believes supports it. Python decides the lines.

The algorithm

It runs once, after generation. Raw tokens stream to the UI while the model writes; the backend’s final done event carries the grounded text, which replaces the stream. The pass runs in a worker thread, and if it throws, the raw answer is kept and the error logged.

For every parenthesized group that contains a Belge N reference:

  1. Take the cited sentence. It is the text between the previous citation (or sentence end) and the opening parenthesis. A sentence ends at a newline, or at ., ! or ? followed by whitespace and an uppercase letter, including Ç, Ğ, İ, Ö, Ş, Ü. The first version split on any period, so “saat 23.50’de” cut the sentence in half.
  2. Turn the sentence and every line of every document into token sets.
  3. In document N, find the best window of one to three consecutive lines.
  4. If the window clears the thresholds, rewrite the citation to Belge N, satır X-Y. If it does not, rewrite it to Belge N and drop the line part.

Tokenization is where Turkish matters:

_TOKEN = re.compile(r"\d+(?:[.,/:]\d+)+|\d{2,}|[^\W\d_]{3,}")
_TR_UPPER = str.maketrans({"İ": "i", "I": "ı"})

def _tokens(text):
    folded = unicodedata.normalize("NFKC", text.translate(_TR_UPPER)).lower()
    return {
        tok[:5] if tok[0].isalpha() else tok
        for tok in _TOKEN.findall(folded)
        if tok not in _STOPWORDS
    }

Python’s lower() maps “I” to “i”, which is wrong for Turkish, so the dotted and dotless capitals are translated first. That way “YILDIZ” in a header matches “Yıldız” in the answer. Numbers with separators stay whole (“13/01/2026”, “10:40”, “1.8”), and single digits are dropped because they match everything. Words are cut to five characters as a crude stemmer for an agglutinative language: “kompartıman”, “kompartımanda” and “kompartımandaki” all become “kompa”. Stopwords cover function words and the boilerplate of every official document (“edilmiştir”, “bulunmaktadır”).

The window search is a short scan:

for each start line s:
    hits = |sentence ∩ line[s]|
    for the next up to 2 lines e:
        grown = |sentence ∩ (line[s] ∪ … ∪ line[e])|
        if grown - hits < 2: stop growing        # a stray common word doesn't extend the range
        hits = grown
    keep the window with most hits; on a tie, the shorter one

A window is accepted with at least 2 hits covering at least 30% of the sentence’s tokens. The scan is linear in the number of lines, so its cost is negligible next to generation.

Thresholds and score bands

The same problem shows up in a second place. When Tiro builds its case wiki, a sub-model extracts facts with a quoted excerpt, and align() locates it in three tiers: exact substring, whitespace-normalized substring, then token-set overlap. If no tier matches, the fact is dropped.

The fuzzy tier accepted a span at 0.4 overlap, which meant most of the excerpt’s words could be missing from the lines it pointed at. None of the six call sites passed a stricter minimum. I raised the floor to 0.7.

There was a second bug in the scoring. Exact matches scored 1.0, whitespace matches 0.9, and fuzzy matches 0.5 + 0.4 * overlap. At full overlap that is exactly 0.9, so a caller asking for min_score=0.9 to exclude fuzzy matches could still get one. The fuzzy formula is now 0.5 + 0.35 * overlap, which with the 0.7 floor gives a band of 0.745 to 0.85. The three bands no longer overlap, so a threshold between them does what the caller expects.

Strictness matters more for us than for a web service. A desktop install has no central log and no kill switch. A bad citation goes to the lawyer’s screen and I never hear about it, and the only rollback is a new installer.

The idea we rejected

The first version tried to be helpful. If document N did not carry the sentence, it moved the citation to whichever other document matched best, under stricter thresholds (3 hits, 50% share).

Here is a sentence I constructed against the demo file:

Meryem Demirci, Bilgin’in adı geçtiğinde hiç duraksamadığını söylemiştir (Belge 5, satır 70).

“Meryem Demirci said she did not hesitate at all when Bilgin’s name came up.” Document 5 has no line that supports it, so the first version went looking elsewhere and moved it to document 7, line 36. That line is from the inspector’s report and says her statement recorded that she hesitated when Bilgin’s name came up. The citation made the opposite of the record look sourced.

Two things cause this. Names, “ifade”, “söyledi”, “sanık” and “olay” appear in almost every document of a criminal file, so there is always some document with plenty of overlapping words. And Turkish puts negation inside the word: “duraksamadığını” and “duraksadığı” differ by the “-ma-” suffix, and both become “durak” after stemming. A lexical matcher cannot see “did not”.

The rule now: a citation stays in the document the model named. If that document doesn’t support the sentence, the lawyer sees a bare “(Belge 5)” and reads it themselves. A citation only moves when the model cited a document number that doesn’t exist in the case file at all, since then there is nothing to keep.

How we measure it

The eval is 78 questions over the demo case, with gold answer substrings taken from the source files: 46 fact, 10 cross-document, 8 law, 10 not-in-file, 4 opinion. A script sends each question to a running backend and parses the final answer. For each (Belge N, satır X-Y) citation on an answerable question, it counts the citation as supporting if lines X-1 to Y+1 of document N contain one of the gold substrings.

On the 33 answerable questions the set had when grounding landed, supporting citations went from 4 of 52 to 40 of 54, and correct answers from 26 to 30. That commit also labelled retrieved passages with their real line ranges and added a reranker, so the jump belongs to the whole change; no run isolates re-anchoring alone. Later runs on the full set of 64 answerable questions land between 75 of 107 and 76 of 102, and one run moves by about two answers either way, so I only trust differences across whole runs.

Bare “(Belge N)” citations are not counted at all, in either direction. Dropping a line number removes a citation from the denominator. The metric rewards precision and says nothing about how often we give up.

What it still gets wrong

The pass finds the lines that carry the sentence’s words, which are sometimes different from the line that carries the fact. From the eval:

Maktulün kompartıman kapısı, 7. vagon kondüktörü Mehmet YILDIZ tarafından yedek anahtarla açılmıştır (Belge 2, satır 11).

Line 11 of the scene report has “7. vagon kondüktörü Mehmet YILDIZ tarafından”, five hits. The spare key is on line 13, four hits. Line 12 between them adds only one word, so the window never grows to reach line 13. The citation is on the wrong line by two.

Name-heavy claims can anchor on a statement header that just lists the names. A date in the answer loses to the descriptive words around it when they sit on another line, and OCR adds noise (“adli’emanet”). On a real case file the supporting rate is clearly lower than on the clean demo, and I don’t yet know how much of that is OCR, how much is our gold substrings, and how much is the matcher.

One idea I want to try next is to anchor on the answer’s key entities and numbers first, and use the rest of the sentence only to break ties.
