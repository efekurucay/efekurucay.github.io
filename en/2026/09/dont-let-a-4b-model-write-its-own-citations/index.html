Don’t let a 4B model write its own citations

30 September 2026 · writing · history

In Tiro, the desktop assistant we’re building for Turkish criminal defense lawyers, the case file never leaves the laptop. So the model is small: Gemma 4 E4B, 4-bit quantized, running through llama.cpp. When it answers, it cites the file like this: “(Belge 3, satır 34)”, document 3, line 34. The lawyer clicks it and the document opens with those lines highlighted.

A wrong line number is worse than none, because it looks checked.

The problem

Our demo case is a fictional file called “Doğu Ekspresi Cinayeti” (Murder on the Orient Express). When we asked the model about the victim’s blood alcohol, we got answers like this:

Maktulün kanında 1.8 promil alkol tespit edilmiştir (Belge 3, satır 37/1).

The sentence is right. Document 3 is the autopsy report, also right. But “37/1” is not a line. It’s TCK 37/1, the joint perpetration article from the demo indictment. The model found something number-shaped in its context and put it where the line number goes. The value is on line 34.

This wasn’t a one-off. On our demo eval, 4 of 52 line citations pointed at a line that contained the answer.

The reason is simple. A line number has no semantic link to the sentence. The model writes “1.8 promil alkol” fine because the words mean something. “34” means nothing. And the context is full of article numbers, dates, times and the line labels of other passages. A 4B model has a hard time copying the right one out of all that.

The fix: code picks the lines

I stopped treating the model’s line numbers as data. The model decides which sentence it’s writing and which document supports it. After generation, a small Python pass picks the lines.

For every “(Belge N, satır X-Y)”:

  1. Take the sentence the citation belongs to.
  2. Turn the sentence and every line of document N into sets of words.
  3. Find the run of 1 to 3 consecutive lines that shares the most words with the sentence.
  4. If there are at least 2 shared words covering at least 30% of the sentence, replace the line range with that run. If not, drop the line part and keep just “(Belge N)”.

Turkish makes this harder. Python’s lower() turns “I” into “i”, which is wrong in Turkish, so we map the capital İ and I ourselves first. That way “YILDIZ” in a header matches “Yıldız” in the answer. For suffixes we use a crude stemmer: the first 5 letters of each word. “kompartıman”, “kompartımanda” and “kompartımandaki” all become “kompa”. Dates like “13/01/2026” and numbers like “1.8” stay in one piece.

Being strict matters more in a desktop app. There’s no central log and no kill switch. A bad citation goes straight to the lawyer’s screen and I never hear about it.

The idea we dropped

The first version tried to be more helpful. If the model cited the wrong document, it moved the citation to whichever other document shared the most words.

Here is a sentence I made up against the demo file:

Meryem Demirci, Bilgin’in adı geçtiğinde hiç duraksamadığını söylemiştir (Belge 5, satır 70).

“Meryem Demirci said she did not hesitate at all when Bilgin’s name came up.” Nothing in document 5 supports it. The first version moved the citation to document 7, line 36. That line is from the inspector’s report and says the opposite: she hesitated when Bilgin’s name came up.

Two things cause this. Names and words like “ifade” (statement), “söyledi” (said) and “sanık” (defendant) appear in almost every document of a criminal file, so some document always matches well. More importantly, Turkish puts negation inside the word. “duraksamadığını” (that she did not hesitate) and “duraksadığı” (that she hesitated) differ only by the “-ma-” suffix, and after stemming both become “durak”. A word-matching method can’t see “not”.

The rule now: a citation stays in the document the model named. If no line supports the sentence, the lawyer sees just “(Belge 5)” and reads the document. A citation to the right document without a line number is safer than a precise citation to the wrong one.

Results

A citation counts as correct if its lines, plus one line above and below, contain the answer. With this change, citations landing on the right lines went from 4 of 52 to 40 of 54 on the demo eval. The same commit also gave retrieved passages their real line labels and added a reranker, so not all of that jump belongs to this pass.

The metric has a blind spot. Citations reduced to a bare “(Belge N)” aren’t counted at all. So it measures precision, not how often we give up.

Where it still fails

The pass finds the line that carries the sentence’s words, which isn’t always the line that carries the fact. From the eval:

Maktulün kompartıman kapısı, 7. vagon kondüktörü Mehmet YILDIZ tarafından yedek anahtarla açılmıştır (Belge 2, satır 11).

Line 11 has “7. vagon kondüktörü Mehmet YILDIZ tarafından”, 5 shared words. The spare key is on line 13, 4 shared words. The citation lands two lines off.

Name-heavy sentences sometimes anchor on a statement header that only lists the names, and OCR’d documents add noise. On a real case file the rate is clearly lower than on the demo, and I don’t yet know how much of that is OCR and how much is the matcher. The next thing I want to try is anchoring on the names and numbers in the answer first, and using the rest of the sentence only to break ties.
