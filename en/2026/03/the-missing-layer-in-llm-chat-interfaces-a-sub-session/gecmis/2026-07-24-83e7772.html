The Missing Layer in LLM Chat Interfaces: A Sub-Session Protocol

21 March 2026 · writing · history

This project is still a work in progress. But the problem it solves is real.

Every LLM chat interface works the same way: one flat, linear context window. You start with a math question, shift to debugging code, then jump to something philosophical — and the entire history keeps stacking up. Token by token. Topic by topic.

It feels invisible at first. Until you realize the model is still reading twenty messages about calculus every time you ask a physics question.

What’s Actually Happening

After 20 messages on derivatives, you switch to kinematics. The context sent to the model? Still carrying your entire calculus thread. On every. Single. Query.

This is context bloat — and the consequences are real:

  • Model attention dilutes across irrelevant history
  • Users resort to opening new chats or manually summarizing just to stay focused
  • No platform handles this in any standardized way

Existing approaches — RAG, summarization, window trimming — are all reactive. They kick in after the problem has already formed.

The Idea: Model Subsession Protocol

MSP is a lightweight, open standard proposal for nested, isolated topic sessions inside a single parent chat.

The concept: instead of opening a new chat every time you switch topics, you open a sub-session within your current conversation. That sub-session is:

  • Isolated — its messages don’t pollute the parent context by default
  • Context-aware — it can selectively pull a summary or recent messages from the parent
  • Summarizable — when closed, it produces a compact summary that can optionally merge back into the parent
Main Session
├── [messages 1-20] ← Topic: Calculus
├── SubSession: "calculus-limits" (isolated)
│   ├── "what is a limit?"
│   └── "explain epsilon-delta"
├── [messages 21-35] ← Topic: Physics
└── SubSession: "physics-kinematics" (isolated)
    ├── "what is velocity?"
    └── "solve this kinematics problem"

Where It Stands

The project is at v0.1.0 — actively in progress, not finished. But the core is working:

  • Formal protocol specification written (spec/SPEC.md)
  • JSON Schema definitions complete (Draft-07)
  • TypeScript reference library built: SessionManager, SubsessionManager, ContextBuilder
  • Unit tests written, CI/CD pipeline live

To make it concrete:

const session = new SessionManager('study-session');
session.addMessage('user', 'I need to study for my exam.');
session.addMessage('assistant', 'What subject should we start with?');

const calculus = session.openSubsession('calculus-review');
calculus.addMessage('user', 'Explain limits');
calculus.addMessage('assistant', 'A limit is the value a function approaches...');

calculus.close('Covered limit fundamentals.');
calculus.mergeToParent();

When you open a physics sub-session afterward, the calculus detail stays out of context — only its summary comes through.

Why Now

Context management has become one of the most talked-about challenges in LLM engineering. Longer context windows don’t solve the problem — they just delay it. A bigger bucket is still a full bucket.

MSP takes a different approach: instead of expanding context, it proposes structured isolation — shaping context per topic, per intent. It’s model-agnostic, platform-agnostic, and requires no changes to underlying LLM APIs.

What’s Next

An npm package is coming. A Python SDK is planned. MCP server integration is on the roadmap. But the real goal isn’t just another tool — it’s a standard.
