Task

The week 3 energy accounting lab: one Sky UDP client sends numbered messages to one Sky UDP server, and both print Powertrace lines every 30 seconds. Three scenarios run on the same topology for the same 15 simulated minutes, and the logs show where each mote’s time goes: CPU, low power mode, radio transmit and radio listen. From that the average current and a rough battery lifetime follow.

Code

The client and server are Contiki 3.0’s examples/udp-ipv6 programs with Powertrace added: #include "powertrace.h" and powertrace_start(CLOCK_SECOND * 30) right after PROCESS_BEGIN().

Two problems had to be solved before the lab worked:

  • No packet left the client. The client printed every TX: Hello N, but no radio frame followed and the server received nothing — the unmodified udp-ipv6 example failed the same way. The Sky platform sets UIP_CONF_ND6_SEND_NA 0 in contiki-conf.h: IPv6 neighbour discovery is off because RPL is expected to fill the neighbour table. With two motes and no RPL root the table stayed empty and uIP dropped every packet. Both programs now add the other mote to the neighbour table (add_neighbor(), link-layer address derived from the IPv6 interface identifier).
  • ROM overflow. With Powertrace and ContikiMAC the server did not fit into the Sky’s 48 KB of flash. DEBUG_NONE in both programs and CFLAGS += -DUIP_CONF_TCP=0 (TCP is unused) fixed it; the TX: and Server received: lines are plain printfs so the packet delivery ratio can still be counted.

Calculations

The counters are cumulative, so every row uses the difference of two consecutive lines of the same mote: ΔCPU, ΔLPM, ΔTX, ΔRX, and ΔT = ΔCPU + ΔLPM.

  • CPU duty cycle = ΔCPU / (ΔCPU + ΔLPM) × 100
  • TX % = ΔTX / ΔT × 100 · Listen % = ΔRX / ΔT × 100 · Radio on % = (ΔTX + ΔRX) / ΔT × 100
  • Iavg = Σ Di × Ii with CPU 1.8 mA, LPM 0.0545 mA, TX 17.4 mA, listen 18.8 mA
  • Lifetime = 2500 mAh (two AA cells) / Iavg

Example, scenario B, server, 150 s → 180 s: ΔCPU = 15641, ΔLPM = 967049, ΔTX = 3730, ΔRX = 8650, ΔT = 982690 → CPU 1.59 %, TX 0.38 %, listen 0.88 %, radio on 1.26 %. powertrace_to_csv.py does this for every interval and writes the CSV columns Time, Mote, CPU %, LPM %, TX %, RX %, Radio On %.

Why the results look like this

  • Listening dominates. In A the radio transmits 0.02 % of the time, yet listening is 99.6 % of the average current (18.8 of 18.88 mA). The cost of a sensor node is waiting for data, not sending it: idle listening.
  • Duty cycling removes it. ContikiMAC wakes the radio 8 times per second for two short channel checks and sleeps otherwise. Listen time falls from 100 % to about 1 %, the server’s current by a factor of 55, lifetime from 5.5 days to about 300 days, and PDR stays at 100 %.
  • The sender pays for the rendezvous. With ContikiMAC a frame is repeated until the receiver wakes and acknowledges it, so TX time rises from 0.02 % to about 0.5 %, and the client, which sends, draws more than the server.
  • Energy follows traffic. Three times more packets in C raise TX time about 2.5×, listen time about 1.6× and CPU time about 1.8×; the server’s current rises by 73 %. Without duty cycling the cost is constant and high; with it, it grows with the traffic.

Limitations

  • Simulated radio: UDGM without interference or loss, two motes, one hop — no collisions, retransmissions or forwarding load.
  • Constant datasheet-style currents; no battery voltage drop, self-discharge or temperature. Sensors and LEDs are not counted.
  • 15 minutes of steady traffic extrapolated to months.
  • In a multi-hop network the nodes near the sink forward everyone’s traffic and would run out first.
